# ADR

ADR значит Architecture Decision Record.

В этом проекте ADR - короткая запись принятого архитектурного решения: какую
проблему решали, какое правило выбрали, почему оно важно для Calls и какие
ограничения приняли вместе с ним.

ADR нужен не для описания всего проекта. Он фиксирует решения, которые влияют на:

- границы сервиса;
- внутреннюю архитектуру: слои, зависимости, направление импортов;
- Kafka-договор;
- смены статусов звонка;
- хранение данных;
- надёжность: idempotency, locks, retry, outbox, DLQ;
- метрики и поведение в production.

ADR не является:

- roadmap;
- списком идей;
- задачей на будущее;
- пересказом кода;
- местом для общих рассуждений.

Если код меняет правило из ADR, сначала надо обновить или заменить ADR. Иначе в
проекте появятся два разных источника правды.

## Когда нужен ADR

Новый ADR нужен, если решение трудно безопасно вывести только из кода или README.

Примеры:

- меняем границы `Domain`, `Application`, `Infrastructure` или `app`;
- разрешаем новому слою зависеть от Laravel, БД, Redis или Kafka;
- меняем Kafka key, payload, topic или правило обработки плохого сообщения;
- меняем state machine звонка или поведение late events;
- меняем способ брони оператора, retry, outbox или DLQ;
- переносим тяжёлые метрики из snapshot в `/metrics` или наоборот;
- меняем production-процессы, без которых сервис не работает.

ADR не нужен для мелкой правки текста, переименования локальной переменной,
обычного теста или исправления бага без изменения правила.

## Внутренняя архитектура

Внутренняя архитектура - это правила устройства кода внутри Calls.

Для этого проекта сюда относятся:

- какие слои есть: `Domain`, `Application`, `Infrastructure`, `app`;
- кто от кого может зависеть;
- где живут бизнес-правила звонка;
- где живёт Laravel-код;
- где маппятся Eloquent records в доменные объекты;
- где открываются транзакции;
- где пишутся адаптеры Kafka, Redis, outbox, DLQ и метрик;
- какие объекты repository может вернуть в `Application`.

ADR по внутренней архитектуре нужен, если изменение меняет эти правила, даже
если Kafka-договор, схема БД и публичные команды остаются прежними.

## Что фиксировать в ADR по внутренней архитектуре

Такой ADR должен прямо отвечать:

- какую границу слоя меняем;
- почему старого правила не хватает;
- какое новое правило вводим;
- какие зависимости теперь разрешены или запрещены;
- где должен жить новый код;
- как это проверить тестом или проверкой границ архитектуры;
- какие старые варианты больше нельзя использовать.

Пример: если решаем, что `Application` может получать Eloquent model из
repository, это нужен ADR. Такое решение меняет границу слоя и влияет на весь
код, даже если внешнее поведение сервиса не изменилось.

Каждый файл отвечает:

- какая была проблема;
- какое правило приняли;
- как это должно работать;
- что нельзя делать;
- какие минусы приняли.
