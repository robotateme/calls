# ADR-0001: Calls держит только локальную бронь оператора

Status: Accepted

## Проблема

Calls должен выбрать оператора для входящего звонка. Одновременно могут работать
несколько queue workers.

Если два workers увидят одного свободного оператора, они могут назначить его на
два разных звонка. Это нельзя допустить.

При этом Calls не владеет настоящей доступностью оператора. Поля `available` и
`afk` приходят извне. Calls не знает, ушёл ли оператор в разговор, освободился
ли он после разговора или стал недоступен по другой причине.

## Решение

Calls хранит только короткую локальную бронь:

- `operators.reserved_call_id`;
- `operators.reserved_at`.

Это значит:

- `available` и `afk` - внешняя информация;
- `reserved_call_id` и `reserved_at` - локальная защита Calls от двойного
  назначения;
- после `connected` Calls снимает бронь, но не выставляет `available=true`.

## Как выбирать оператора

Оператор подходит только если всё верно:

- `available=true`;
- `afk=false`;
- `reserved_call_id is null`.

Выбор и запись брони должны происходить в одной DB transaction.

## Как освобождать бронь

Release очищает бронь только у того оператора, который держит этот call:

- можно очистить `reserved_call_id`, если он равен текущему call;
- нельзя очищать чужую бронь;
- после `connected` бронь надо снять;
- менять `available` после `connected` нельзя.

## Зависшие брони

Если worker умер или retry flow оборвался, бронь может зависнуть.

Для этого есть отдельная компенсация:

```bash
php artisan calls:operator-reservations:release-expired
```

Это нормальная cleanup-задача. Это не повод передавать Calls владение
доступностью операторов.

## Что нельзя делать

- Нельзя использовать `available=false` как локальную бронь Calls.
- Нельзя выставлять `available=true` после `connected`.
- Нельзя считать, что Calls управляет разговором после соединения.
- Нельзя освобождать бронь без проверки `reserved_call_id`.

## Минусы

- Нужно чистить expired reservations.
- Нужны проверки от гонок между workers.
- Если появится отдельный operator-service, с ним понадобится явный контракт
  reservation/release.

## Что отклонили

- Менять `operators.available` внутри Calls: это смешивает внешнюю доступность и
  локальную бронь.
- Не хранить бронь вообще: workers смогут отправить одного оператора в два
  звонка.
- Вынести allocation в отдельный dispatch-service прямо сейчас: это возможное
  будущее, но не нужно для текущего сервиса.
