# ADR-0006: Kafka - основной канал сервиса

Status: Accepted

## Проблема

Calls получает входящие звонки, отправляет команды в Telephony и принимает факты
обратно от Telephony.

Эти события не похожи на обычный HTTP-запрос:

- звонок может обрабатываться дольше одного HTTP-запроса;
- Telephony может ответить позже;
- сообщение может прийти повторно;
- важен порядок событий одного звонка;
- при падении Calls входящие факты нельзя потерять;
- несколько consumers должны делить нагрузку.

Если сделать главный вход через HTTP, Calls станет сам отвечать за буферизацию,
повторы, порядок, сдерживание нагрузки и восстановление после падений.

Если использовать только Redis queue, получится внутренняя очередь одного
сервиса, а не договор между Calls и Telephony.

## Решение

Kafka - основной внешний канал Calls.

Через Kafka идут:

- входящие звонки в topic `incoming-calls`;
- факты Telephony в topic `telephony.facts`;
- команды Calls в Telephony через topic `telephony.commands`.

HTTP не является входом обработки звонка. HTTP ограничен `/metrics`.

Redis queue используется только внутри Calls для jobs и повторов. Она не заменяет
Kafka и не является межсервисным договором.

## Почему так

Kafka даёт нужные свойства для обработки звонка:

- хранение сообщений: сообщение не пропадает при рестарте Calls;
- consumer groups: можно запускать несколько consumers;
- offset: понятно, что уже прочитано;
- порядок внутри partition для одного key;
- lag: если Calls отстаёт, это видно, а события не теряются;
- повторное чтение для диагностики и восстановления после исправления кода.

Для Calls это важнее, чем простота HTTP endpoint.

## Правила

- Входящий звонок принимается из Kafka, не через HTTP.
- Facts от Telephony принимаются из Kafka.
- Commands в Telephony публикуются в Kafka только из `telephony_outbox`.
- Kafka topic, type, schema_version и payload являются внешним договором.
- Redis queue используется только после чтения Kafka-сообщения, внутри Calls.
- Плохое Kafka-сообщение идёт в DLQ, а не угадывается обработчиком.
- Для всех сообщений одного звонка Kafka key равен `external_call_id`.

Правило про key отдельно зафиксировано в
[ADR-0003](0003-kafka-message-key-external-call-id.md).

## Последствия

Плюсы:

- Calls можно останавливать и поднимать без потери входящих событий;
- Telephony и Calls не должны ждать друг друга синхронно;
- нагрузку можно делить между consumers;
- Kafka lag показывает, что сервис не успевает;
- порядок событий одного звонка можно держать через key.

Минусы:

- нужен Kafka broker в окружении;
- нужны consumer groups, offsets и мониторинг lag;
- локальная проверка сложнее, чем простой HTTP-запрос;
- producer обязан соблюдать schema_version, type, payload и key;
- плохие сообщения надо разбирать через DLQ.

## Нельзя

- Добавлять HTTP endpoint как главный вход для звонков.
- Отправлять команду Telephony напрямую, минуя `telephony_outbox`.
- Использовать Redis queue как межсервисный канал.
- Обрабатывать нарушение Kafka-договора как нормальное событие.
- Коммитить offset до того, как сообщение безопасно обработано или записано в
  DLQ.

## Отклонили

- HTTP callbacks от Telephony как главный вход.
- Redis queue как внешний договор между сервисами.
- Прямой синхронный вызов Telephony из Calls.
- Хранить входящие события только в таблице БД без Kafka.
- Один общий topic без строгих типов сообщений.
